# 设计与研究纲要（给维护者）

> 一句话：**程序只负责「感知 + 留痕」，一切判断归 LLM。**
> 这不是「教室借用效率工具」，而是一个 **LLM-agent 安全性实践项目**。

## 0. 定位与研究问题

上一版交付（`NJU_Yuque` 的 `classroom` 模块）被判定失败：不是功能不行，而是**它把 LLM 去掉了**
——时间归一化、节次推算、四档判定、草稿识别全硬编码成 Python 规则，LLM 只剩「调一个已经写好判断的程序」。
本项目的立场相反：规则用**举例式提示词**表达，遇到没枚举到的情况由 LLM 自己拿主意，
优化目标是**误操作最少、最安全**（不是省 token）。背景与对照表见 `README.md`。

**核心研究问题**：如何做出一个「误操作最少、最安全」的 LLM-agent？

**本项目的答案**：安全的第一道闸门是「**本次会话注册了哪些工具**」（能力边界），
而不是提示词里的道德约束。日常轮询会话里 agent 手里**根本没有**删文档 / 移目录的工具，
「想误操作也无从下手」；只有每周六的归档会话才把这批写工具挂上去。
「能力分级」是本项目最重要的**可做实验的变量**。

第二个研究问题是**可观测性**：每次 run 的完整 session
（系统提示 → 变更报告 → 每步思考 → 每次工具调用 → 结论）必须原样留档，
并对外露出两个「看板」：知识库里的《Agent 通知》文档（本周期通知，最新的在最上面）与
8787 端口的 `/log` 页（每轮的结论），供人复查、调试、改进工作流。

> **改代码前先读 [`principles.md`](principles.md)**：那条纪律（程序不越界、禁止语义闸门）
> 落到具体改动上就是「什么该写进 Python、什么只能写进提示词」。

## 1. 系统全景

周期定义、目录形态与归档判据见 §2.1（这里是全局流水，不重复）。

```
┌─ 感知层（程序，常驻，不含任何 LLM 调用）──────────────────────────────┐
│  watcher（轮询，默认 60s；发现变化后等 45s 静默期再叫 LLM）            │
│    拉 TOC + 文档列表 → 快照 → 与上一轮 diff                           │
│    三层筛子：updated_at → 正文哈希 → 占位标题+空正文                   │
│    筛完为空 → 本轮静默结束（0 token）                                  │
│    筛完还有东西 → 唤醒 判断层（kind=polling），看到的是**最终状态**      │
│  timer（时钟，每周六 00:00 = 周期翻转时刻）                             │
│    无条件唤醒 判断层（kind=archive）—— 即使知识库一个字都没变            │
└───────────────────────────┬──────────────────────────────────────────┘
                            ▼  变更报告 / 归档指令（纯客观事实，不含任何判定字段）
┌─ 判断层（LLM，每次唤醒 = 一个独立 run + 一个独立 session）────────────┐
│  prompts/polling.md   日常轮询的「工作说明书」                         │
│  prompts/archive.md   归档会话的「工作说明书」                         │
│  工具集（按 run 类型分级注册，这是安全闸门）：                          │
│    通用   kb_tree / dir_list / doc_read / ws_* / emit_* / done        │
│    归档+  toc_create / toc_move / toc_remove / doc_create / doc_delete│
│  agent loop（手搓）：LLM ↔ tool call 循环，直到调用 done 或触顶         │
└───────────────────────────┬──────────────────────────────────────────┘
                            ▼  产出（结构化，落盘到工作区）
┌─ 留痕层（程序）──────────────────────────────────────────────────────┐
│  runs/<run_id>/session.jsonl  本次 run 的完整留痕（唯一事实来源）        │
│  runs/<run_id>/result.json    本轮结论                                 │
│  outbox/applications/         申请 JSON（交给「发起借用」的同学）        │
│  outbox/notify/pending/       通知事件（→ 投递层）                      │
│  → 对外：《Agent 通知》文档（本周期通知）+ 8787 `/log`（每轮结论）       │
└───────────────────────────┬──────────────────────────────────────────┘
                            ▼  （可选，独立项目：QQ 桥）
┌─ 投递层（**另一个仓库**，见 docs/interface.md）────────────────────────┐
│  QQ 桥：扫 pending/ 按 seq 发 QQ → 移进 done/                          │
│  入站：白名单命令；/run /archive /apply 写 control/requests/ 交给核心    │
│  **不轮询、不写 outbox/ 产物**（state.json 只有一个写者）               │
└──────────────────────────────────────────────────────────────────────┘
```

## 2. 两个入口

| | `polling`（事件驱动） | `archive`（时钟驱动） |
|---|---|---|
| 触发 | 轮询发现变化，**三层筛子剩下来的不为空**，且**静默期已过** | 每周六 **00:00**（= 周期翻转时刻，可配） |
| 输入 | 变更报告 | 归档指令（含当前周期 + 完整目录树） |
| 工具集 | 通用（**语雀侧接近只读**） | 通用 + 结构写工具 |
| 为什么 | 社员随时在写文档，agent 不该同时有写权限（社员误拖 vs agent 误删，两边都容易出事） | 上一周期已收尾、下一周期还没开始，是**唯一安全的结构维护窗口** |

### 2.1 「周期」的定义（关键）

**一个周期 = 周六 00:00 ~ 下周五 23:59，目录名就是这两天的日期**（如 `0919-0925`）。

为什么不是「周一~周日」：教室必须**提前 2 天、最多 9 天**申请，所以一个周期里所有活动
——包括周日活动的申请——最晚在周五就提了。**周六 00:00 一到，这个周期的申请就一定已经处理完毕。**
把周期起点定在周六 00:00，就让**归档时刻与周期翻转时刻完全重合**，不再有任何日历错位。

```
周六      周日      周一      周二      周三      周四      周五
9/12     9/13     9/14     9/15     9/16     9/17     9/18   ← 周期 0912-0918
9/19     9/20     9/21     9/22     9/23     9/24     9/25   ← 周期 0919-0925  ← 今天 9/20 在这里
9/26     9/27     9/28     9/29     9/30     10/1     10/2   ← 周期 0926-1002
```

归档会话的知识库目标形态（**顺序是硬要求**，2026-09-26 出过一次顺序错）：

```
教室借用申请
├── 指导文档（必读）     第 1 位：系统性文档，只读
├── Agent 通知           第 2 位：程序自己维护（本周期通知，最新的在最上面），周期更替时清空
├── 0919-0925           第 3 位：【当前周期】有且只有一个
└── 归档区               第 4 位：永远在最末
    ├── 0912-0918       内部**新在上、旧在下**
    └── 0905-0911
```

> **根目录允许四类东西**：① 系统性文档（《指导文档（必读）》《Agent 通知》）；
> ② **有且只有一个**当前周期目录；③ 「归档区」（在最末，内部新→旧）。
> 纯目录变化不算「需要处理的事」（`Changes.empty` 只看文档级变更），
> 所以这两篇系统性文档摆在那里不会惹麻烦。
>
> ⚠️ **顺序为什么容易错**：`toc_create` 与 `toc_move`（不带 `prepend`）都是「**追加到末尾**」——
> 新建周期目录会被追加到归档区**下面**，刚归档的周期会被追加到归档区**底部**。
> 所以 `prompts/archive.md` 里写死了目标顺序（`root_target_order`）+ 工具语义 + **整理完必须重新
> `kb_tree()` 核对**（那次事故就是「以为排好了、没再读一遍」）。要让节点落到最前用
> `toc_move(..., prepend=true)`。

归档的判定规则（写进了 `prompts/archive.md`）：

1. 当前周期目录在根目录 → 不动；在归档区 → 搬回来；都没有 → 建；
2. 根目录里**早于**当前周期的周期目录 → **全部**归档（支持进程停摆多周期后的补跑）；
3. **晚于**当前周期的目录 → 一律不碰（将来可能允许提前一整周申请、同时存在多个活跃目录，**待定**）。

### 2.2 时区：钉死 `Asia/Shanghai`，不跟服务器设置走

核心判定全挂在「今天」上：**申请周期**、**可借日期 = 今天 +2 ~ +9 天**、**每周六 00:00 归档**。
而云服务器（阿里云 / 腾讯云 / 大多数 VPS）**默认就是 UTC**。按服务器本地时间算的话：

1. **归档晚 8 小时**触发（北京周六 00:00 = UTC 周五 16:00，得等到 UTC 周六 00:00）；
2. 每天有 **8 小时窗口**「今天」算错一天——而这恰好是判定申请合不合规的依据。

所以时区在 `clock.py` 里**钉死**：不管 `TZ` 环境变量和 `/etc/localtime` 是什么，
`clock.now()` 永远返回上海时间。**部署时不需要任何时区配置。**
（不用写死 `+08:00` 偏移，是为了表达「哪个**时区**」而不是「偏移几小时」；`tzdata` 已进化依赖，
所以 Windows 上行为与 Linux 一致。）

**这条纪律由测试守着**（`tests/test_clock.py`）：它用 **AST 扫描** `src/`，
发现 `clock.py` 之外还有 `datetime.now()` / `date.today()` 就直接失败。
为什么要用「扫源码」这种重手段：时区是「**全项目一起守才有效**」的约定——
后来任何一处顺手写的 `datetime.now()` 都会让那份逻辑重新跟回服务器时区，而且**不会报错**，
只在 UTC 服务器上错。（用 AST 而不是文本匹配，是因为文档串里会引用 `datetime.now()` 作反例。）

## 3. 工作区布局

一切运行时状态都在 `workspace/` 下（`.gitignore` 已排除）：

```
workspace/
├── state.json                     程序侧记忆：上一轮快照（TOC + 每篇的 updated_at / 正文哈希）、
│                                  静默期计时 pending_since / pending_polls、归档水位线、
│                                  《Agent 通知》doc_id、当前周期 active_cycle、清单指纹 plan_notified
├── runs/<run_id>/
│   ├── payload.json               程序给 LLM 的输入原文（变更报告 / 归档指令）
│   ├── session.jsonl              完整 session（唯一事实来源）
│   ├── result.json                本轮结论（verdict / 用量 / 产出 / 停止原因）
│   └── notice.json                这一轮跑完后《Agent 通知》的刷新结果（程序做的）
├── control/requests|done/         外部（QQ 桥）→ 核心的唯一触发通道，见 docs/interface.md §1.2
├── outbox/
│   ├── applications/<id>.json     一份受理的申请一个文件（幂等）
│   ├── applications/index.json    索引（扫目录重建）
│   └── notify/
│       ├── pending/*.json         待投递的事件
│       ├── done/*.json            投递方挪进来即视为已投递
│       ├── unrouted/*.json        （投递层）认不出人的事件，等人补映射
│       ├── failed/*.json          （投递层）坏文件，不堵队列
│       ├── .seq                   单调递增的序号计数器
│       ├── outbox.jsonl           只追加的审计流水（投递方**不要**读它）
│       └── delivery.jsonl         （投递层）投递审计：每条一行，含目标与结果
└── notes/                         LLM 自己的跨轮记忆（agent 可读可写；唯一允许它写的目录）
```

> 没有 `session.md` 这回事：要看细节用 `yqa render <run_id>`（人话版留痕），
> 或者直接读 `session.jsonl`；对外只露结论（`/log` 与《Agent 通知》）。
> 本地不落第二份渲染副本，避免两份真相漂移。
> 服务器的目录布局（`/opt`、`/var/lib`、凭证）见 `docs/deploy.md` §2。

## 4. 变更报告：程序 → LLM 的输入

**原则：只给客观事实，一个判定字段都不给。** 程序不标「这是草稿」，不标「这条不合规」——
「草稿标了一半误提交」这种情况程序根本判不了，但 LLM 能。

```jsonc
{
  "run_id": "20260920-101834-polling-7d44",
  "kind": "polling",
  "at": "2026-09-20T10:18:34+08:00",     // 「今天」以它为准
  "repo": { "namespace": "<group>/<repo>", "toc_sha": "31ea039222dd55ca" },
  "first_run": false,
  "toc_changed": true,
  "toc": [ { "uuid": "…", "type": "TITLE|DOC", "title": "…", "depth": 1, "path": "…",
             "parent_uuid": "…", "doc_id": 0 } ],   // 全量目录树
  "docs": {
    "added":   [ { "doc_id": 1, "title": "…", "dir": "0919-0925", "author": "张三",
                   "created_at": "…", "updated_at": "…", "preview": "正文前 300 字" } ],
    "updated": [ { …, "prev_title": "…", "prev_updated_at": "…", "prev_dir": "…" } ],
    "removed": [ { …, "last_seen_at": "…" } ]          // 不带正文，不占预算
  },
  "counts":  { "added": 1, "updated": 0, "removed": 0 },  // 真实总数
  "notes":   [ "程序想说的话（合并了多少次轮询、剔除了哪些占位文档…），不是判定" ],
  "toc_only": [ { "doc_id": 1, "title": "只被挪了目录的文档" } ]
}
```

- `preview` 由程序截取前 300 字，目的是让 LLM **大多数情况下不必再调 `doc_read`**（省一轮往返，不是省判断）。
- `toc` 全量给出（含 `doc_id` 与 `parent_uuid`），因为「文档在哪个目录」是判断依据之一（在归档区 = 别再处理）。
- `docs.*` 可能因 `max_docs_per_run` 被截断，此时 `notes` 里会有说明。

## 5. 工具集（分级 = 安全闸门）

参数表在代码里（`tools.py` 的注册表就是权威，提示词与它由测试盯着不许漂），这里只记**分工**：

| 通用（polling 与 archive 都有） | 作用 |
|---|---|
| `kb_tree()` | 知识库目录树（uuid / 层级 / 每个目录的文档数） |
| `dir_list(dir)` | 列某目录下所有文档（不只是本轮变过的） |
| `doc_read(doc)` | 读全文 markdown（截断到 8000 字） |
| `ws_list` / `ws_read` / `ws_write` | 工作区读写；`ws_write` 只能写 `notes/` 下（跨轮记忆） |
| `emit_application(...)` | 产出一份申请 JSON（程序做查表归一化，见 §7.2） |
| `emit_notice(...)` | 产出一条通知事件（`kind` 受 `LLM_NOTICE_KINDS` 闸门限制） |
| `done(verdict, summary)` | 结束本轮，给判定摘要（唯一的正常出口） |

| 仅归档会话追加 | 作用 |
|---|---|
| `toc_create(title, target_uuid?)` | 新建一个 TITLE 节点（下一周期目录） |
| `toc_move(node_uuid, target_uuid?, prepend?)` | 移动节点；不带 `target_uuid` = 根目录，默认落**末尾**，`prepend=true` 落**最前** |
| `toc_remove(node_uuid, with_children?)` | 从目录移除节点（**不删文档**） |
| `doc_create(title, body?, parent_uuid?)` | 新建文档（重建被删的《指导文档》） |
| `doc_delete(doc_id, reason)` | 删除文档，`reason` **必填**（理由会写进 session 留痕被人复查） |

> 客户端的 `yuque.toc_rename()`（实测 `editNode` 有效）**没有开放给 agent**——
> 目录改名风险高又难判定，只留给人工/脚本（见 D9）。

### 5.1 三条硬性安全设计

1. **能力分级**：日常会话**不注册**任何结构写工具。不是「注册了但提示词叫它别用」，而是**工具根本不存在**。
2. **工作区沙箱**：所有文件写操作的路径都做规范化 + 前缀校验，越界直接报错返回给 LLM（让它自己纠正）。
3. **`--dry-run`**：所有写操作（语雀 + 工作区）变成「只记录不执行」，用于开发期与预演。

> 反模式记录：**不要**给这个 agent `bash`。给 shell 等于放弃能力边界，安全研究就此失去抓手。

## 6. session 格式（JSONL，一行一事件）

```jsonl
{"t":"run_start","at":"…","run_id":"…","kind":"polling","model":"deepseek-flash","repo":"…","dry_run":false,"tools":["kb_tree","…"]}
{"t":"system","content":"<prompts/polling.md 全文>"}
{"t":"user","content":"<变更报告 JSON>"}
{"t":"assistant","step":1,"content":"…","reasoning":"…","tool_calls":[{"id":"c1","name":"doc_read","arguments":"{…}"}],"usage":{"in":1234,"out":56,"total":1290,"cached":0},"finish_reason":"tool_calls","ms":2100}
{"t":"tool","step":1,"call_id":"c1","name":"doc_read","args":{…},"ok":true,"result":{…},"ms":210}
{"t":"run_end","steps":2,"tool_calls":2,"verdict":"accepted","summary":"…","stop_reason":"done","error":"","usage":{…},"emitted":[…],"kb_writes":[]}
```

- 存**原始** `reasoning_content`（DeepSeek 的思维链）——这正是「为什么它这么判」的证据。
- `run_start` 里的 `tools` 是**本轮实际注册的工具名单**——事后查「它当时到底有没有能力删文档」，看这一行就够。
- 每写一行都 flush（进程被杀也留得下现场）；损坏的行跳过而不是整份作废（`read_events`）。
- 渲染成人话是**按需**的：`yqa render <run_id>`（工具调用与思考过程都在）；
  对外只露结论——《Agent 通知》文档与 8787 的 `/log` 页都不含工具调用。
- session 是**唯一事实来源**：任何「它当时到底怎么想的」的疑问都以它为准。

## 7. 输出契约（留给另外两位同学）

> **完整契约见 [`docs/handoff.md`](handoff.md)**（字段表、用法、消费约定、本 agent 的「不做」清单）。
> 样例文件在 [`examples/`](../examples/)。这里只记设计决策。

### 7.1 `activity` 直接对齐 `crb` 的 `Activity`

下游（教室借用插件 / `crb plan`）是**纯程序**，它不会替你猜「仙林」是 `"3"`、「仙II区」是 `"12"`。
所以申请 JSON 里的 `activity` 就是 crb `Activity` 的原样，配套的 `yqa export-plan`
把它们汇总成下游能直接吃的 `plan.json`：

```bash
yqa export-plan -o plan.json --defaults '{"JYDWDM":"400760","JSJYLXDM":"02"}'
crb plan --file plan.json --save
```

### 7.2 「LLM 给原话、程序查表」的分界线

这是本项目最重要的一条分工线，落到代码上是三个层次：

| 层次 | 归谁 | 例子 |
|---|---|---|
| 自然语言 → **规范写法** | **LLM** | 「下午4点到6点」→ `16:00`/`18:00`；「仙二」「仙2区」「逸夫楼A」→ 规范名 `仙II区`/`逸夫楼A区`；判断是不是草稿、该不该退回 |
| 规范写法 → 学校代码 | **程序**（`school.py` 查表） | 苏州 → `"4"`；`仙II区` → `"12"`；`16:10-18:00` → 节次 `7-8` |
| 占用情况 → 去哪间教室 | **下游**（有学校登录态） | 意向教室被占 → 同一时段、同一教学楼随机 |

**这条线具体怎么划**（2026-09-26 按负责人意见厘清——原先含糊，我一度写成「查表全归程序」）：

* **写法归一归 LLM**：社员的写法五花八门（「仙二」「仙2区」「逸夫楼A」「第二教学楼」…），
  归一成规范名这件事 **LLM 比程序强得多**，别名表/正则追不上；
* **规范名 → 代码归程序**：这是**查表**（测量，不是判断），填错一个代码会让下游去查错的教学楼；
* 两边靠**同一份表**对齐：`school.BUILDINGS`（四个校区共 16 栋，拿登录态从学校接口现查）
  随每轮的变更报告下发（`school.facts()`），提示词只说「归一到 `school.buildings` 里的名字」。
  —— **不抄进提示词**是因为那份表随学期会变，抄进去必然漂；
* 程序侧**只做精确查表**（2026-09-27 删掉了原先那套 `_canon_name` 模糊匹配）：
  键与学校系统里的写法逐字一致（`仙II区` 与 `仙Ⅱ区` 是两个字符串），LLM 塞进来一个
  变体就查不到 → 留空。**不兜**的理由：兜住等于把「LLM 没归好」这件事藏起来，
  而兜错就是把下游引到**另一栋**教学楼——留空只退化成同校区随机，代价小得多；
* 认不出来的教学楼**宁可留空（= 随机）也不猜**（`tests/test_school.py` 锁死）。

### 7.3 通知事件

格式见 `docs/handoff.md` §3（`kind` 词汇表也在那儿）。两条设计决策：

* **投递方是独立项目**（QQ 桥，2026-09-24 拆出，见 [`interface.md`](interface.md)）。它遵守一条
  本项目特有的纪律——**发送失败就停下本轮**，不在 `pending/` 里跳着发，这样 `seq` 顺序不会被破坏。

  没有 `target` 时由桥按人名映射（`docs/handoff.md` §3）。

**不保证能借到**。因此「目标教学楼无空闲教室 → 退回」这条判定**做不到**，已下移到下游

## 8. 三个「不要为噪声付钱」的设计（实测踩出来的）

### 8.1 静默期合并（debounce）

语雀手工建一篇文档会**分几步**产生变更：先出现一个无标题空文档 → 改标题 → 写正文保存。
每一步都是一次 diff，不处理的话一篇文档就要唤醒三到五次 LLM。

做法：发现变化后**先不叫 LLM**，并把**基线快照摇在那里**（不推进），
等知识库安静 `quiet_seconds`（默认 45s）后再拿**当时的最新状态**一次性处理。

三个附带好处：

1. **LLM 看到的是最终状态**，而不是中间那个「无标题空文档」——判断质量反而更好；
2. 建完又立刻删掉 / 改了又改回去 → 静默期结束时 diff 为空 → **整轮根本不触发**（0 token）；
3. 静默窗口内**不读正文**（反正还不能决定），省下一批 API 调用。

实测：模拟「建空文档 → 改标题 → 写正文」三次变更（12 秒内）→ **只跑 1 次**（之前是 13 次）。

**静默期只对常驻轮询（`yqa run`）生效。** 人工命令（`yqa once`）会**关掉**它
（`debounce=False`）——你刚写完文档敲下命令，就该立刻看到结果，而不是被告知「没有变化」
然后白等 45 秒。静默期要治的噪声是「语雀分步投稿」，**人工敲键盘不是噪声**。

> **踩过的坑（实测）**：`yqa once` 一度忘了传 `debounce=False`，于是写完文档立刻跑
> 会被报「知识库没有变化」——**把「在静默期」说成了「没变化」**，让人以为程序坏了。
> 根因是 `cli.py` 那一行**接线**没有任何测试守着。现在 `tests/test_cli.py` 用
> **行为断言**（写完立刻 once 必须唤醒）+ **接线断言**（直看 `debounce` 参数）双管，
> 同时 `Runner.last_skip` 会如实区分 `"no_change"` / `"quiet_period"`，提示语不再可能说假话。

**`--force` 和静默期的边界**（容易搞混）：`--force` 的含义是「无视 **diff**」，不是「无视**静默期**」
（有意设计，由 `test_debounce.py::test_force_bypasses_nothing_but_still_needs_quiet` 锁住）。
但在**命令行**这一层不一样：`yqa once` 自己就关了静默期，所以 `once` 与 `once --force`
只要敲下去都会真跑。两层语义不同，写在这里以免下次又踩。

### 8.2 忽略自己写的文档（防自激）

《Agent 通知》（以及 2026-09-26 之前的《工作日志》）就存在被监控的知识库里。
程序写完它之后，下一轮轮询会看到「它变了」→ 唤醒 LLM → 又写 → **自激循环，停不下来**。

做法：`Settings.ignore_doc_titles` + `State.notice_doc_id`，取快照时直接把程序自己维护的文档剔除
（标题匹配兼顾首次部署，doc_id 兼顾改名）。

> 教训：**监控系统必须把自己造成的副作用排除在信号之外**，否则反馈回路会把账单烧穿。
> 实测：一篇测试文档曾触发 13 次 run，其中 **8 次**是这个循环，每轮白烧 5k token。

### 8.3 占位标题过滤（比草稿标记更早一级）

语雀新建文档时标题默认是 **`无标题`**（官方 API，实测）或 **`无标题文档`**（网页端）。
**这不是社员写的，是机器生成的占位符**，不可能携带任何借用意图。

于是有三道筛子，一层比一层早：

| 筛子 | 谁生成 | 谁判 | 漏网时怎么办 |
|---|---|---|---|
| **占位标题 + 空正文** | 机器 | **程序**（精确字符串） | 标题改一个字就立即失效，照常交付 LLM |
| 草稿标记（含删了一半） | 人 | **LLM**（模糊语义） | 提示词里给例子 |
| 归档区里的任何东西 | 人 | **LLM** | 提示词里给例子 |

**分界线**：机器生成的精确哨兵归程序，人写的模糊标记归 LLM。

**为什么还要加「且正文为空」**：如果社员手快、直接点进正文粘内容而没改标题，
那他是真想申请。只看标题会把他静默丢掉——这是本项目最不能接受的失败模式。
正文一有内容就不是中间态，照旧交给 LLM。
安全取值：**正文读不到时不做剔除**（宁可白跑一轮，也不漏掉真实申请）。

> 实现上的坑：这个筛子必须在 ``enrich_and_refine`` **之后**跑（要正文），
> 但必须在**静默期判定之前**跑（否则占位文档仍然会启动计时器）。
> 好在前者本来就要读变更文档的正文，所以**零额外请求**。

### 8.4 相关：`Changes.empty` 不算目录变化

**新建一篇文档必然会在目录里加一个节点**，如果 ``toc_changed`` 也算「有变化」，
上面两道筛子全会被目录变化抵消掉。所以：

* ``empty`` 只看**文档级变更**（新增/修改/删除）；
* 目录层面的真实变化其实已经在文档级反映出来了（文档被挪位置 → ``dir`` 变 → 算 ``updated``）；
* 纯目录变化（建了个空分组、调了下顺序）信号极低，交给每周六的归档会话。

## 9. 提示词（举例式，不穷举）

`prompts/polling.md` 的写法约定：

1. 交代身份与目标（你是这个知识库的负责人）；
2. 交代**必须知道的事实**（可借日期 = 今天+2~+9 天、08:00–22:20、午饭时段、节次表、周期含义）；
3. 交代**工作流**（先看变更报告 → 只读你有疑问的那几篇 → 产出 → done）；
4. **给例子**，不给穷举规则：标准填法 / 模糊写法（`9月16日`、`下午4点-6点`、`仙林校区`）/
   边界（`八点到九点`、`17:00-16:00` 填反了）/ **草稿标记删了一半**（仍按草稿处理）；
5. 明确「不要做」的事：不要读无关文档、不要试图理解整个知识库。

> 设计原则：**能用例子讲清的就不要写成规则条文。** 规则的穷举是上一版失败的原因。

## 11. 开发期踩到并写进代码的坑

这几条都是**真金白银踩出来的**，直接决定了架构：

| # | 现象 | 结论 |
|---|---|---|
| P1 | 语雀 `GET /repos/{ns}/docs/{doc_id}` 是 **404**，只能用 slug | 客户端自己做 `doc_id → slug` 缓存（`resolve_slug`） |
| P2 | 语雀在**目录位置发生变化**时也会 bump 文档的 `updated_at` | **必须**加「正文哈希」第二道筛子，否则会给社员误发「你改了文档」的通知。见 `snapshot.enrich_and_refine` |
| P3 | 语雀目录**读写有秒级延迟**，写完立刻读看不到 | 写后 `wait_toc_settled()`；提示词里明确写「不要因为看不到就重试」（否则会重复建目录） |
| P4 | 按节点自身的 `path` 当文档所在目录是**错的**（那会变成「父目录/文档名」） | 抽出 `yuque.doc_dir_map()`（只认 `parent_uuid`）统一处理；根目录下的文档 `dir == ""` |
| P5 | 把程序自己维护的文档（当年是《工作日志》，现在是《Agent 通知》）挂进目录后，**它自己就成了知识库里的一个文档** → 程序写它的动作变成下一轮的变更信号 → **自激循环**（实测：一篇文档触发 13 次 run） | 解法**不是**「把它挪出目录/砍掉可见性」，而是**把自己的写入排除在信号之外**（§8.2）；同时 `Changes.empty` 不看 `toc_changed` |
| P6 | Windows 控制台是 GBK，rich 打 emoji 直接 `UnicodeEncodeError` 崩掉 | 入口 `_force_utf8()`；控制台文案不用 emoji（markdown 里照常用） |
| P7 | **语雀读回来的 markdown 与写进去的不完全一样**：它会拆「跨代码段的粗体」（`**第一行** \`x\` **整行删掉**` 读回来是 `**第一行 **\`x\`** 整行删掉**`），也会吃掉标题行后面那个空行 | ① 源文件里**别写跨代码段的粗体**；② **程序生成/上传的正文必须与「读回来的形式」逐字一致**——否则「内容变没变」的幂等判断永远为真，每轮刷新都白写一次（2026-09-26 在 `noticedoc.render` 与 `cli._fill_notice_link` 上各踩一次，两处都有测试钉着） |
