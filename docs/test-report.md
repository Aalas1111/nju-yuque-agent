> 「给能力但不滥用」这件事，在这个案例上是可观测的。

## 4. 测试过程中发现并修复的真 bug

### Bug 1：归档日历口径错位（会导致误归档正在使用的周目录）

* 现象：2026-09-20（周日）用 `week_of(today)` 算「本周」得到 `0914-0920`，于是归档会话会把根目录里**正在用的** `0921-0927` 归档掉。
* 原因：归档定在**周六**，而目录按**周一~周日**命名，两者存在一个自然天的错位。
* 修复：新增 `week.archive_targets()`——
  * 该归档的 = **最近那个归档日所在的那一周**；
  * 该启用的 = **归档日之后那个周一所在的一周**。
* 验证：`tests/test_week.py::test_archive_targets` 覆盖 8 个时刻；并验证「同一周期内结果稳定」（防常驻进程重启后重复归档）。
* 附带论证：因为教室必须提前 48 小时申请，周日活动的申请最晚周五就提了，**周六归档不会漏任何申请**，所以不用改目录命名。

### Bug 2：`updated_at` 被语雀无谓 bump → 给社员误发 tampered

* 现象：`runs/20260920-102205-polling-7eb6` 里，`思维训练营第3期` 被报为「改动」，agent 据此发出了 `tampered` 通知。
  但我根本没动过那篇文档——它只是被挪了目录。
* 原因：语雀在文档的目录位置变化时也会更新 `updated_at`。
* 修复：`snapshot.enrich_and_refine()` —— `updated_at` 变了**才**去读正文算哈希，
  `sha256(title + 正文)` 也没变就丢掉这条变更（记为 `toc_only`，只在报告的 `notes` 里提一句）。
* 验证：`tests/test_snapshot.py::test_updated_at_only_change_is_filtered_out_by_content_hash`；
  另外做了一次确定性实测：手工篡改 `state.json` 里某篇文档的 `updated_at`（正文不动），
  跑 `yqa once` → 输出「知识库没有变化，未唤醒 LLM」。
* **设计意义**：「内容到底变没变」是**测量**，不是判断，所以它归程序——这和「草稿算不算数」归 LLM 并不矛盾。
  这条线是：*程序负责可测的事实，LLM 负责不可测的语义。*

### 附带修的两处

* `doc_dir_map`：文档所在目录**不能**取节点自身的 `path`（那是「父目录/文档名」）。
* 留痕文档**正常挂进目录**（社员看得见），但程序把它从变更信号里剔除——
  详见 §8.4 和 §9（这是一个「自己的写入变成信号」的坑，曾经造成自激循环）。

## 7. 第二轮：归档周期重构（2026-09-20 下午）

### 7.1 改了什么

原来的设定是「归档在周六 08:00，目录按周一~周日命名」，两者错位 8 小时 + 一个自然天，
导致周日跑归档会去归档**正在用的**目录（Bug 1）。

**新设定**（由需求方拍定）：

* 一个**申请周期 = 周六 00:00 ~ 下周五 23:59**，目录名就是这两天的日期（如 `0919-0925`）；
* 归档时刻 = **周六 00:00**，与周期翻转**完全重合**，错位消失；
* 周期内部发起归档也安全：当前周期目录缺就建、有就不动；**早于**当前周期的一律归档；
  **晚于**当前周期的一律不碰（D8）。

### 7.2 实测

| # | 动作 | 结果 |
|---|---|---|
| M1 | 知识库迁移：`0921-0927` → `0919-0925`、`0914-0920` → `0912-0918` | ✅ 用实测可用的 `editNode` 改名（新发现：目录节点**可以**改名） |
| A2 | 在根目录故意留一个过期周期目录 `0905-0911`，跑 `yqa archive --dry-run` | ✅ 正确识别为需要归档（只发一次操作） |
| A3 | 跑**真实** `yqa archive` | ✅ `0905-0911` 真的被移进「归档区」，且排在 `0912-0918` 下方（最新在上）；根目录回到「指导文档 + 0919-0925 + 归档区（最末）」 |
| A4 | 清理测试遗留目录 `0905-0911` | ✅ |

### 7.3 本轮又抓到的两个问题

**Bug 3：dry-run 下 agent 会反复重试。**
dry-run 时写操作不真执行，但 agent 会去读回来确认，发现“没生效”就重发。
第一次实测里同一个 `toc_move` 发了 **3 次**。
修复：dry-run 时程序会在变更报告里明确加一条 note——“写操作不会真正生效，读回原状属预期，不要重试”。
重测后只发 1 次。

**Bug 4（可测性）：归档时刻不能被注入。**
`Runner.archive_once()` 写死 `datetime.now()`，导致整条归档路径无法用固定时刻测试。
修复：`archive_once(*, now=None)`，由常驻循环传入当前时刻——路径现在完全可复现。

### 7.4 新增测试

* `tests/test_week.py` 重写为**周期**语义：周期边界、七天归属、跨年、稳定性（同一周期内结果不变）、“归档时刻 ≡ 周期翻转时刻”。
* 新增 `tests/test_watcher.py`（14 条）：静默性、归档触发时机（8 个时刻 × 水位线的组合）、同周期不重复归档、跨周期再触发、补跑、禁用开关、单轮异常不致命。

## 8. 第三轮：交接契约对齐 `crb`（2026-09-20 晚）

### 8.1 发现的问题（严重）

原来的申请 JSON 给的是**人名**（`campus: "仙林"`、`building: "仙II区"`）和 `start/end`，
而下游是**纯程序**：

* `crb` 的 `Activity.campus` 要的是**校区代码** `"3"`，塞「仙林」进去→查不到教室→申请静默失败；
* `building` 要的是 **`JXLDM`**（如仙林 `"11"`），塞「仙II区」→ 0 条结果；
* `crb` **不会**从 `16:10-18:00` 推算节次，它要的就是 `period: "7-8"`。

→ **按原格式交接，crb 是吃不了的。**

### 8.2 修法：把 `activity` 做成 `crb.Activity` 的原样

新增 `school.py`（校区代码表 / 教学楼代码表 / 节次表 / 可借日期窗口），并在工具层做归一化：

| 层次 | 归谁 | 例子 |
|---|---|---|
| 自然语言 → 语义 | LLM | 「下午4点到6点」→ `16:00`/`18:00`；「南京大学苏州校区」→ 苏州 |
| 语义 → 学校代码 | **程序**（查表） | 苏州 → `"4"`；仙II区 → `"12"`；`16:10-18:00` → 节次 `7-8` |
| 占用情况 → 去哪间教室 | **下游** | 意向教室被占 → 同时段同教学楼随机 |

**关键安全属性**：认不出来的教学楼**留空（= 随机）也不猜**——参见
`tests/test_school.py::test_normalize_building_unknown_is_empty_not_a_guess`。

新增 `yqa export-plan`，把申请汇总成下游能直接吃的 `plan.json`（已实测生成 4 条活动，字段与 crb 完全对齐）。

### 8.3 顺带修正的两处旧文档错误

| 旧说法 | 修正 | 依据 |
|---|---|---|
| 「必须提前 48 小时」 | **可借日期 = 今天 +2 ~ +9 天** | 谷和平 对借用页面的实测记录 |
| 「活动日期距今 >14 天 → 受理+提醒」 | 删掉（被 9 天上限取代，改为**硬性退回**） | 同上 |

### 8.4 发现并修掉的 Bug 5：《工作日志》不在目录里

上一轮我把《工作日志》**故意不挂进目录**（怕破坏「根目录只有一个周期目录」的不变式），
导致需求方在语雀侧边栏看不到它。已改为正常挂进目录，并相应修改归档提示词
（《指导文档》《工作日志》都是**系统性文档**，归档会话不得动它们）。
实测：`yqa archive --dry-run` 已正确识别并保留它们（`kb_writes == []`）。

### 8.5 新增能力：`yqa once --rescan`

## 9. 第四轮：噪声治理（2026-09-20 深夜）

### 9.1 需求方报的问题

> 「人手工建一次文档会触发很多次 agent 的处理，token 消耗大增。」

查工作日志硬证据：建一篇文档产生了 **13 次 run**。

```
11:34:34 unrecognized    ┐
11:35:09 nothing_to_do   │ 语雀分步建文档（无标题空文档 → 改标题 → 写正文）
11:35:49 rejected        │
11:36:46 unrecognized    │
11:37:34 accepted        ┘
11:38:15 nothing_to_do   ┐
11:38:52 nothing_to_do   │ 8 次，每 ~37s 一次，停不下来
…                        │
11:42:29 nothing_to_do   ┘
```

前 5 次是语雀产品设计导致的，**后 8 次是另一个 bug**：
逐轮 `payload.json` 显示变更文档全是 `['工作日志']`——
**程序把运行记录写进《工作日志》，而《工作日志》就在被监控的知识库里**，
于是「写日志 → 日志变了 → 唤醒 LLM → 又写日志」形成**自激循环**。

### 9.2 两个修复

| # | 修复 | 机制 |
|---|---|---|
| F1 | **静默期合并** | 发现变化先不叫 LLM，**基线快照摇在那里不推进**，等知识库安静 `quiet_seconds`（默认 45s）再拿**当时的最新状态**一次性处理 |
| F2 | **忽略自己写的文档** | `Settings.ignore_doc_titles` + `State.journal_doc_id`，取快照时剔除程序自己产出的文档 |

F1 的三个附带好处：LLM 看到**最终状态**而非中间态；建完又删/改回原样 → **整轮不触发**；
静默窗口内**不读正文**（省 API 调用）。

F3（顺手修的）：**首次运行不再白叫 LLM** —— 那一轮的报告本来就是空的，叫醒它只会得到一句「无事可做」。

### 9.3 实测对比

| 动作 | 修复前 | 修复后 |
|---|---|---|
| 「建空文档 → 改标题 → 写正文」（12 秒内 3 次变更） | 5+ 次 run（其中至少 4 次是噪声） | **1 次 run** |

## 10. 第五轮：占位标题过滤（需求方提议）

### 10.1 提议与评估

需求方提议：语雀新建文档时标题是「无标题文档」，**日常轮询阶段永远不为它唤醒 agent**；
但任何改动（哪怕是错字「无标题文」）都要能筛出来，然后照旧走静默期。

我的评估：

| | 结论 |
|---|---|
| 方向 | ✅ 采纳。它比静默期**更靠前**：静默期是「延迟判断」，它是「直接排除在信号之外」 |
| 分层 | ✅ 占位标题是**机器生成的精确哨兵**，归程序；草稿标记是**人写的模糊标记**，归 LLM |
| ⚠️ 漏洞 | 只看标题的话，**社员手快直接粘正文、没改标题**的真实申请会被静默丢掉 |
| ✅ 补法 | 条件收紧为「**标题是占位符 且 正文为空**」；正文一有内容就照常交给 LLM |
| 实测发现 | 官方 API 在 title 为空时自动填的是 **`无标题`**（不是「无标题文档」）——两个都要收 |

### 10.2 实现中踩到的第三个坑

加上过滤后测试仍然失败，原因：**新建一篇文档必然会在目录里加一个节点**，
于是 ``Changes.empty`` 里的 ``toc_changed`` 总是 True，把过滤效果抵消了。

修法：``empty`` 只按**文档级变更**判；纯目录变化（建空分组、调顺序）不再唤醒轮询。
这不是损失——文档被挪位置本来就会以 ``updated``（``dir`` 变了）的形式出现在文档级。

### 10.3 活体验证

同时造两篇占位标题文档，各 120 秒内观察：

| 文档 | 内容 | 结果 |
|---|---|---|
| A | 标题 `无标题文档` + 正文空白 | ✅ **完全没唤醒 LLM**（程序剔除） |
| B | 标题 `无标题文档` + 正文是完整申请（忘了改标题） | ✅ **唤醒了**，产出 `rejected` 通知：<br>「标题还是语雀默认的占位标题……标题就是活动名称，缺了它没办法往下走。麻烦你把标题改成活动名字——**正文里的信息我都看到了，没有问题，不用重填**」 |
| 整批 | —— | ✅ **只 1 次 run** |

### 10.4 新增测试

`tests/test_placeholder.py`（16 条）：纯函数（剔除/保留/空白/读不到/删除/空列表）、
新建空文档不唤醒、API 默认占位 `无标题` 也筛、错字标题立即失效、
**占位标题但有正文必须唤醒**（安全属性）、删空白占位不报警、
过滤发生在静默期之前、占位→真标题仍走静默期、剔除数写进报告、长期无人管的空文档不卡死。

同时修正 `tests/test_snapshot.py`：`toc_changed` 会被记录，但**单靠它不足以唤醒**。

当前全量：**173 passed**，`ruff check` 全绿。

### 10.5 三道筛子一览

```
语雀里发生变化
   ↓
① updated_at 变了？           —— 没变就不看（最便宜的筛子，不多打一个接口）
   ↓ 变了
② 正文哈希也变了？           —— 没变就丢掉（语雀挪目录也会 bump 时间戳）
   ↓ 变了

   ↓

```

## 11. 第六轮：部署到阿里云（2026-09-21）

第一轮真正的**服务器部署**（阿里云轻量/ECS，Ubuntu 24.04，2 核 2G，华东）。
部署本身很顺（`uv sync` → `yqa doctor` 全绿 → systemd 常驻），
但**真机上暴露了两个离线测试完全没盖住的 bug**——两个都是「fake 太善良」造成的。

### 11.1 Bug 6：`dir_list` 会把根目录的文档混进任意目录

`tools.py` 里的过滤条件是：

```python
if not (path == wanted or path.endswith("/" + wanted) or path == ""):
```

最后那个 **`path == ""`** 让「根目录下的文档」匹配**任意**目录。于是
`dir_list("归档区/0912-0918")` 会把根目录的《指导文档》《工作日志》一并返回。

**危险在哪**：归档会话里 LLM 如果信了这个结果，就会以为这两篇系统性文档在归档区，
**可能把它们从根目录搬走**。这一轮没出事是因为模型自己起了疑心——它的思考里写着：

> *"Hmm, dir_list seems to return the same docs regardless? Both return 指导文档 and 工作日志.
> That's odd."*

然后它改用 `kb_tree` 的 `docs_here: 0` 推出了正确结论。**等于靠模型的怀疑捡回一条命**，
这不能算设计。修法：`path == ""` 只在显式要根目录时才算匹配（新增 `dir: "."` 写法）。
回归测试见 `tests/test_dir_list.py`（6 条）。

### 11.2 Bug 7：《工作日志》每跑一轮就在文末多堆一份表头

`journal.py` 原本靠一个 HTML 注释当定位标记：

```python
MARKER = "<!-- NEWEST -->"
if MARKER not in body:
    body = f"{HEADER}
{body}"      # ← HEADER 里就带着 MARKER
head, _, tail = body.partition(MARKER)
```

问题在于**语雀读回来的 markdown 是规范化过的**：HTML 会被剥掉
（`<!-- NEWEST -->` 没了，`<details>` 也没了），引用的换行也被重排。所以
`MARKER not in body` **永远成立** → 把 HEADER 贴上去 → 接着在刚贴的 HEADER 里
找到了标记 → `head` = 表头、`tail` = **整份旧正文**。

结果：`new_body = 表头 + 标记 + 新节 + 旧正文`，**每跑一轮文末就多一份表头**，
日志会无限膨胀。部署后第一次归档会话（08:20:38）就复现了：

```
# 工作日志          ← 表头
## 2026-09-21T08:20:38 · archive · nothing_to_do   ← 新节
# 工作日志          ← 表头又一份
```

修法：**改用结构定位**——找第一节的标题（`## <时间戳>`），这个在语雀的规范化里能活下来。
不再依赖任何 HTML 标记。回归测试见 `tests/test_journal.py`
（含一条「连写 10 次，表头必须只有 1 份」）。

### 11.3 为什么测试没能盖住

两条都是 fake 的错，而且错得很典型：

| bug | fake 干了什么 | 真实语雀干了什么 |
|---|---|---|
| Bug 7 | 测试把带标记的**原始 HEADER** 原样喂回去（`body=f"{HEADER}

## 旧的…"`），标记还在，于是走了「正确」分支 | **把 HTML 标记剥掉**，于是永远走「没有标记」分支 |
| Bug 6 | 旧的工具测试**根本没测 `dir_list`**（`tests/` 里一次都没出现过） | —— |

教训：**fake 要比被测代码更「不友好」**。凡是真实系统会做的规范化/裁剪，
fake 都得照着做一遍，否则测试测的是「代码在我的想象里能不能跑」。

### 11.4 顺带发现：冷启动会立刻跑一次归档

全新部署（没有 `state.json`）时，`last_archive_title` 是空的，
于是 `archive_due()` 立刻为真 → **第一次 tick 就跑一轮归档会话**（本次约 2.1 万 token）。

这不是 bug（它顺带把知识库结构体检了一遍，本次结论是 `nothing_to_do`），
但值得知道：**冷启动那一下是有成本的**。等这一轮跑完水位线就落上了，
之后要等下一次周期翻转才会再跑。
