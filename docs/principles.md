# 项目规范：判断归 LLM，程序不越界

> 这份文件只讲一条纪律，以及它**为什么**存在。改这个仓库的任何一行代码之前先读它。
>
> 本项目的研究目标：**测试 LLM 在监督、维护一个知识库时的健全性与安全性。**
> 于是「程序该做什么」不是工程习惯问题，而是**实验设计问题**——程序替 LLM 做得越多，
> 被验证的那个能力就越少。

## 1. 一句话

**程序只做「可测量的事实」；语义判断全归 LLM。禁止在程序层对 LLM 的输出做语义审查。**

## 2. 什么算「可测量的事实」（归程序）

| 例子 | 为什么 |
|---|---|
| 轮询 diff（谁在什么时候改了什么） | 测量，不是判断 |
| 正文哈希（内容到底变没变） | 测量 |
| 日历算术（周期、可借日期窗口） | 算术 |
| 查表（校区名 → 代码、`HH:MM` → 节次） | 查表；填错比不填更糟 |
| 状态机（静默期合并、清单指纹去重、`seq`） | 事实与去重 |
| 留痕（session / 产出落盘 / 通知文档） | 留痕 |

## 3. 什么算「语义判断」（只有 LLM 能做，写进提示词）

草稿标记删了一半算不算草稿；时间写法有没有歧义；这条申请该不该退回；通知文案该怎么说；
两篇文档是不是同一件事……**一律归提示词**，不写进 Python。

## 4. 明确禁止：程序层的语义闸门

**不要**在工具层 / 输出层对 LLM 产出的文本做字符串或正则过滤。被明确否决过的反例：

> 在 `tools.emit_notice` 里硬性检测 `message` 出现「改」「改动」就退回重新生成。
> （见提交 `d8cf38f`：试过，按负责人要求撤掉了。）

两个理由：

1. **它会误伤，而且是必然的。** 「改」这个字在正常文案里到处都是
   （`rejected` 通知里「改完保存一下就行」正是**正确**动作）。靠字符串判断语义，
   一定会在某个没想到的句子上判错，而这类误伤没有任何测试能穷举完。
2. **它把研究对象阉割掉。** 要测的就是「LLM 能不能自己守住规矩」。
   程序替它守住了，实验就只剩一个恒为真的断言——项目的研究价值归零。

## 5. 允许的加固方式（按强度从粗到细）

| 手段 | 允许的力度 | 例子 |
|---|---|---|
| **能力边界**（`tools.py` 注册表） | **粗粒度**：有 / 没有这个工具 | 日常轮询根本没有语雀写工具——本项目安全性的落点 |
| **提示词**（`prompts/*.md`） | 规矩 + **为什么** + 正反例 | 文案类规矩**只**写在这里 |
| **守卫测试**（`tests/test_safety.py`） | 盯「契约与提示词漂没漂」、提示词内部自相矛盾 | 不动运行时行为 |
| **契约校验**（`outputs.py`） | **只校验结构**：必填字段 / `schema_version` / `kind` 枚举 | 「格式由程序保证」，不是「语义由程序判断」 |
| ❌ 语义闸门 | **禁止** | 过滤/改写 LLM 的 `message`、按关键词拒收 |

## 6. 写提示词的规矩（拿事故换来的）

1. **写明为什么。** LLM 知道缘由才泛化得对（例：受理后文档已锁定，改了会判「改动无效」）。
2. **例子必须和规矩一致。** 2026-09-25 的现场事故就是：规矩块写了「受理通知不许暗示社员改文档」，
   而同一个文件里的 accepted 例子还写着「把文档改一下告诉我就行」——
   规则改了、例子没改，LLM 上线的行为照着**例子**走。
   → 现在由 `tests/test_safety.py::test_polling_prompt_never_asks_members_to_edit_the_doc` 守着。
3. **能用例子讲清的就别写规则条文。** 规则的穷举是上一版项目失败的原因（`docs/design.md` §0）。

## 7. 改代码前的自问

1. 这件事是**测量/算术/查表/留痕**，还是**语义判断**？后者不该写成 Python。
2. 我要加的这条约束，是「这个工具不存在」（粗粒度、可测）还是「我不喜欢它这么输出」（语义）？
3. 这个规矩能不能只写在提示词里 + 用守卫测试盯着？**能就别写进程序。**
4. 如果确实要动提示词里的规矩：**正例、反例、规矩块必须一起改**，并跑 `tests/test_safety.py`。
